# Frontend

Клиентская часть Avito Yearly Recaps построена на React, TypeScript, Redux Toolkit и Vite.

Основную концепцию и визуальный дизайн интерфейса, а также основной дизайн
recap-карточек разработала
[@Lunkova-Kate](https://github.com/Lunkova-Kate). Отдельные решения по
оформлению карточек и достижений, а также выбору шрифтов обсуждались совместно с
[@alina965](https://github.com/alina965) и остальными участниками команды.

Общее описание проекта, архитектура системы и вклад участников находятся в
[корневом README](../README.md). Основные форматы запросов и ответов описаны в
[контрактах API](../docs/CONTRACTS.md), а роли, метрики, ачивки и действия — в
[каталоге](../docs/CATALOG.md). Share-маршруты перечислены ниже; в контрактах
они пока не описаны.

## Особенности реализации

В Docker-запуске запросы frontend проксирует Nginx. При отдельном локальном запуске эту задачу выполняет dev-сервер Vite.

- состояние серверных данных организовано через Redux Toolkit и RTK Query;
- доступны режим локальных моков и работа с API;
- Vite проксирует `/api` и `/static` на локальный backend;
- пользователь может выбирать профиль, смотреть статистику и достижения, генерировать и открывать итоги года, делиться сокращённой публичной карточкой и получать развлекательное предсказание на следующий год;
- итоги отображаются как карточная карусель с кнопками, индикаторами и клавиатурной навигацией;
- маршрут `/share/:token` отображается отдельной публичной страницей без подключения библиотеки маршрутизации;
- отсутствующие или недоступные изображения заменяются заглушками.

## Поток данных

Статистика и достижения запрашиваются для выбранного профиля. Полученный или сгенерированный recap сохраняется в состоянии страницы и передаётся в `RecapOverlay`, где преобразуется в последовательность карточек:

```text
intro → role → metrics → achievements → action
```

Кнопка «Поделиться» находится в верхней панели `RecapOverlay`. Она вызывает `POST /api/users/{userId}/recap/share`, копирует абсолютную ссылку и показывает уведомление. Публичная страница `/share/:token` затем загружает сокращённый снимок через `GET /api/share/{token}`.

## Запуск на моках

Создайте файл `frontend/.env.local`:

```dotenv
VITE_USE_MOCKS=true
```

Запустите dev-сервер:

```bash
npm run dev
```

Vite выведет адрес приложения в терминале, обычно это <http://localhost:5173>.

В режиме моков backend и PostgreSQL не требуются. В `src/mocks` подготовлены данные для девяти тестовых профилей со статистикой, достижениями, recap и предсказаниями. Созданные share-карточки хранятся в памяти страницы; после перезагрузки доступны детерминированные адреса вида `/share/mock-share-{userId}`.

Переключение между HTTP API и моками выполняется централизованно в базовом RTK Query transport. Endpoint-файлы в обоих режимах используют одинаковые URL, методы, преобразования ответов и правила кеширования. Моки возвращают wire DTO backend, включая `achievements_progress` и `is_complete`. Все ответы проходят проверку на API-границе: повреждённые элементы массивов отбрасываются, отсутствующие поля заменяются безопасными значениями, а wire-поля преобразуются в UI-модель.

## Запуск с API

Сначала запустите backend на `http://localhost:8081`. Например, из корня репозитория:

```bash
docker compose up --build
```

Укажите в `frontend/.env.local`:

```dotenv
VITE_USE_MOCKS=false
VITE_API_BASE_URL=/api
```

После изменения переменных окружения перезапустите Vite:

```bash
npm run dev
```

Если `VITE_API_BASE_URL` не задан, используется `/api`. Dev-сервер Vite проксирует запросы `/api` и `/static` на `http://localhost:8081`.

`VITE_USE_MOCKS` включает локальные данные только при точном значении `true`.

### Публичный адрес share-ссылок

По умолчанию frontend строит абсолютную share-ссылку от `window.location.origin`. Если внешний адрес отличается от адреса, который видит приложение, задайте `VITE_PUBLIC_ORIGIN`, например:

```dotenv
VITE_PUBLIC_ORIGIN=https://recap.example.com
```

Для Docker Compose эта переменная читается из корневого `.env` и передаётся как build argument. После изменения `VITE_PUBLIC_ORIGIN` frontend необходимо пересобрать:

```bash
docker compose up --build frontend
```

Clipboard API обычно доступен только в безопасном контексте — HTTPS или localhost. На HTTP frontend пробует резервное копирование через `document.execCommand('copy')`; если браузер запрещает оба способа, уведомление показывает готовую ссылку для ручного копирования.

## Линтер

Для анализа используется ESLint 10 с flat-конфигурацией из
`eslint.config.js`. Линтер проверяет все файлы `*.ts` и `*.tsx`, каталог
`dist` исключён, так как в нём находится сгенерированный результат сборки.

В конфигурацию подключены готовые наборы правил:

- `eslint:recommended` (`@eslint/js`) ловит обычные ошибки JavaScript —
  например, недостижимый код, повторные объявления и необъявленные переменные;
- `typescript-eslint/recommended` добавляет правила для TypeScript. Часть
  стандартных проверок он заменяет своими версиями, чтобы линтер правильно
  понимал TypeScript-код. В частности, сюда входит проверка неиспользуемых
  переменных;
- `react-hooks/recommended` следит за правильным использованием хуков и их
  зависимостей. Это важно для `useEffect`, `useMemo` и `useCallback`, где легко
  случайно получить устаревшее значение;
- `react-refresh/vite` нужен для корректного обновления компонентов во время
  разработки через Vite Fast Refresh.

Последним подключён `eslint-config-prettier`. Он отключает правила ESLint,
которые могут конфликтовать с форматированием Prettier.

Запуск проверки:

```bash
npm run lint
```

## Форматирование

Для форматирования используется Prettier. Настройки находятся в
`.prettierrc.json`, а файлы и каталоги, которые не нужно проверять, перечислены
в `.prettierignore`.

Отформатировать файлы:

```bash
npm run format
```

Проверить форматирование без изменения файлов:

```bash
npm run format:check
```

## Тесты

Для тестирования используются Vitest, React Testing Library и jsdom.

Тесты находятся в папке `frontend/tests` и повторяют структуру проверяемых слоёв `src`:

```text
tests/
├── features/
├── pages/
├── shared/
└── widgets/
```

Покрыты основные пользовательские сценарии:

- получение и генерация итогов;
- смена профиля и защита от запоздавших ответов;
- загрузка статистики и достижений;
- получение предсказания;
- создание share-ссылки, копирование и резервный сценарий для HTTP;
- загрузка публичной страницы `/share/:token` и обработка недоступного токена;
- ошибки API и повторные запросы;
- `null` и пустые данные;
- навигация по итоговым карточкам с помощью кнопок и клавиатуры.
