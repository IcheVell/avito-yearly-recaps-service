# Avito Yearly Recaps

Сервис анализирует активность тестового пользователя на площадке и собирает персональные итоги года: определяет роль пользователя, выбирает наиболее интересные метрики, показывает полученные ачивки и предлагает следующее действие.

Проект превращает набор разрозненных событий — просмотры, поиски, избранное, объявления, сделки, отзывы, диалоги и посещения — в короткую и понятную историю о том, каким был год пользователя на Avito.

**Демо проекта доступно в открытом доступе:** [http://176.109.107.141](http://176.109.107.141)

## Проблема

За год пользователь совершает на площадке большое количество действий, но обычно не видит их как единую историю. Отдельные просмотры, покупки, продажи, поиски и диалоги сами по себе не создают ощущения прогресса и не дают эмоционального повода вернуться в продукт.

Для Avito это означает упущенную возможность использовать уже накопленные данные не только для аналитики, но и для дополнительного пользовательского сценария, который:

- показывает ценность активности пользователя за прошедший год;
- создаёт эмоциональное завершение года;
- помогает вернуть пользователя в продукт;
- предлагает понятное следующее действие после просмотра итогов.

## Идея решения

Мы предлагаем формат **Avito Yearly Recaps** — персональные итоги года, сформированные на основе реальной активности пользователя.

Backend агрегирует данные пользователя за выбранный год, определяет его основную роль — продавец, покупатель или наблюдатель — и выбирает наиболее характерные метрики. Дополнительно сервис работает с глобальными пользовательскими ачивками и формирует рекомендацию следующего действия.

Вместо простого набора чисел пользователь получает небольшой персональный сценарий:

```text
Активность пользователя
        ↓
Агрегация данных
        ↓
Определение роли
        ↓
Выбор значимых метрик
        ↓
Проверка и получение ачивок
        ↓
Персональный recap
        ↓
Следующее рекомендуемое действие
```

Такой подход должен работать, потому что использует уже существующие продуктовые данные, но показывает их в новой форме: не как статистику ради статистики, а как персональную историю пользователя.

## MVP

Во время хакатона команда реализовала работающий full-stack MVP.

Пользователь выбирает один из тестовых профилей и запускает генерацию итогов. Backend агрегирует годовую активность и формирует recap, в который входят:

- роль пользователя: продавец, покупатель или наблюдатель;
- 0–4 персональные карточки с наиболее интересными метриками;
- 0–3 ачивки;
- рекомендация следующего действия;
- объясняющие данные, на основе которых был сформирован результат.

В MVP уже работают:

- выбор тестового профиля;
- генерация и повторная генерация recap;
- агрегация просмотров, поисков, избранного, объявлений, сделок, отзывов, диалогов и пользовательских сессий;
- определение пользовательской роли;
- выбор наиболее интересных метрик;
- хранение готового recap в PostgreSQL;
- получение статистики пользователя через API;
- проверка правил получения ачивок и их выдача на основе накопленной статистики;
- предсказание на следующий год;
- frontend-интерфейс для просмотра итоговых карточек;
- запуск всего проекта через Docker Compose.

Активный год задаётся на backend через переменную `RECAP_YEAR`. Frontend не передаёт произвольный год в публичном API.

## Ценность решения

Основная ценность подхода в том, что он использует уже существующую активность пользователя и превращает её в новый продуктовый сценарий без необходимости менять основные механики Avito.

Для пользователя решение даёт:

- понятное подведение итогов года;
- персонализацию на основе его реального поведения;
- игровые элементы через роли и ачивки;
- повод поделиться результатом или вернуться к активности;
- понятный следующий шаг после просмотра recap.

Для Avito решение может использоваться как механика вовлечения и возврата пользователей. Тот же подход можно развивать не только для годовых итогов, но и для сезонных, категорийных или событийных recap-сценариев.

Архитектура позволяет отдельно развивать правила выбора метрик, систему ачивок и рекомендации, не меняя формат исходных продуктовых данных.

**Frontend:** React, TypeScript, Redux Toolkit, RTK Query, Vite, Nginx.

**Backend:** Go, Chi, GORM.

**Infrastructure:** Docker, Docker Compose.

PostgreSQL выбран из-за реляционной структуры данных и большого количества связей между пользователями, объявлениями, сделками и активностью. Он удобен для агрегирующих запросов, ограничений целостности и хранения сформированного recap в `JSONB`.

- `service` — координация бизнес-логики, работа с итогами года, статистикой и достижениями.

## Особенности реализации

### Год recap задаётся на backend

Год не передаётся с frontend. Активный год определяется переменной окружения:

```dotenv
RECAP_YEAR=2026
```

Это делает поведение API предсказуемым и не позволяет клиенту произвольно запрашивать recap за неподдерживаемый год.

### Годовая статистика и глобальные ачивки разделены

Recap строится на активности конкретного года, а ачивки могут учитывать накопленную активность пользователя за более длительный период.

Для этого годовые метрики recap и глобальная статистика пользователя рассматриваются как разные сущности.

### Правила ачивок хранятся декларативно

Условия получения ачивок хранятся в PostgreSQL в виде `JSONB`-правил. Backend парсит правило, получает необходимую метрику пользователя и проверяет условие.

Пример простого правила:

```json
{
  "type": "condition",
  "metric": "max_streak_days",
  "operator": ">=",
  "value": 7
}
```

Поддерживаются и составные правила, например несколько условий через `all` или `any`.

Это позволяет изменять пороги и комбинации условий без переноса каждого правила в отдельный участок бизнес-логики.

### Recap сохраняется как готовый результат

После формирования итоговый recap сохраняется в PostgreSQL. Для payload используется `JSONB`, поэтому backend может вернуть уже сформированный результат без повторного конструирования всей структуры на каждый запрос.

### Тестовые данные воспроизводят разные сценарии поведения

Seed содержит тестовые профили и связанную активность: объявления, сделки, отзывы, избранное, поиски, просмотры, сессии и диалоги. Это позволяет демонстрировать различные пользовательские роли, метрики и ачивки без подключения к реальным аккаунтам.


```bash
docker compose down -v
docker compose up --build
```

## API

| Method | Endpoint                           | Назначение                                   |
| ------ | ---------------------------------- | -------------------------------------------- |
| `GET`  | `/api/health`                      | Проверка состояния сервиса                   |

## Безопасность данных

MVP работает с тестовыми данными. В recap используются агрегированные показатели: сервис не выводит личные переписки, данные других пользователей или полный список конкретных покупок.

Такой подход позволяет показать характер активности пользователя без раскрытия лишней информации.

## Ограничения MVP

- используются заранее подготовленные тестовые профили;
- правила генерации рассчитаны на демонстрационный сценарий;
- авторизация и работа с реальными аккаунтами не входят в MVP;
- публичная share-card и полноценная продуктовая аналитика не реализованы.
