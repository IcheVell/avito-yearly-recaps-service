# Avito Yearly Recaps

Сервис анализирует активность тестового пользователя на площадке и собирает связный recap: определяет его роль, выбирает значимые метрики, добавляет уже полученные пользователем ачивки и предлагает следующее действие.

Проект решает две задачи: пользователь получает понятную и эмоциональную историю о своём годе, а продукт — дополнительный сценарий возврата пользователя и продолжения активности.

## Что умеет MVP

Пользователь выбирает один из тестовых профилей и запускает генерацию итогов. Backend агрегирует годовую активность и формирует recap, в который входят:

- роль пользователя: продавец, покупатель или наблюдатель;
- 0–4 персональные карточки с наиболее интересными метриками;
- 0–3 ачивки;
- рекомендация следующего действия;
- объясняющие данные, на основе которых был сформирован результат.

Для демонстрации подготовлены тестовые профили с просмотрами, поисками, избранным, объявлениями, сделками, отзывами, диалогами и историей активности.

## Пользовательский сценарий

```text
Выбор профиля
    ↓
Генерация итогов
    ↓
Агрегация активности за год
    ↓
Определение роли и метрик, получение готовых ачивок
    ↓
Персональный recap
    ↓
Следующее рекомендуемое действие
```

В публичном API год не передаётся с frontend. Активный год задаётся на backend через `RECAP_YEAR`, поэтому клиент не может произвольно запросить итоги другого года.

## Стек

**Frontend:** React, TypeScript, Redux Toolkit, Vite, Nginx. Тесты: Vitest и React Testing Library.

**Backend:** Go, Chi, GORM.

**Database:** PostgreSQL 16.

**Infrastructure:** Docker, Docker Compose.

PostgreSQL выбран из-за реляционной структуры данных и большого количества связей между пользователями, объявлениями, сделками и активностью. Он также удобен для агрегирующих запросов, ограничений целостности и хранения готового recap в `JSONB`.

## Архитектура Frontend


Frontend разделён на слои по ответственности:

```text
src/
app/         Инициализация приложения, Redux-store и providers
pages/       Страницы и композиция пользовательских сценариев
widgets/     Крупные самостоятельные блоки интерфейса
features/    Пользовательские действия и связанная с ними логика
entities/    Доменные типы и компоненты сущностей
shared/      API, конфигурация, общие утилиты и UI-компоненты
mocks/       Локальные данные для запуска без backend
```


Frontend  взаимодействует с backend через RTK Query. Подробное описание структуры, режимов работы, запуска и тестирования находится в [README frontend](frontend/README.md).

## Архитектура backend

```text
HTTP Router
    ↓
Handlers
    ↓
Service
   ↙    ↘
Engine  Repositories
            ↓
        PostgreSQL
```

- `repository` получает и агрегирует данные из PostgreSQL;
- `engine` содержит правила формирования роли, метрик и следующего действия;
- `service` связывает генератор с репозиториями и отвечает за создание/обновление recap;
- `api` содержит HTTP-контракты и handlers.

## Запуск

Для запуска необходимы Docker и Docker Compose.

Для отдельного запуска frontend на моках или через локальный API смотрите [инструкцию frontend](frontend/README.md).

Из корня проекта:

```bash
docker compose up --build
```

После запуска:

- frontend: `http://localhost`
- backend: `http://localhost:8081`
- PostgreSQL: `localhost:5433`

Проверка backend:

```bash
curl http://localhost/api/health
```

При первом создании volume PostgreSQL автоматически применяет:

```text
backend/migrations/000001_init.up.sql
backend/migrations/000002_seed.up.sql
```

Чтобы полностью пересоздать локальную БД и повторно выполнить init-скрипты:

```bash
docker compose down -v
docker compose up --build
```

## API

| Method | Endpoint | Назначение |
| --- | --- | --- |
| `GET` | `/api/health` | Проверка состояния сервиса |

## Ачивки

В MVP ачивки не рассчитываются и не выдаются во время генерации recap. Backend получает уже существующие ачивки пользователя из базы данных и добавляет их в итоговый сценарий.

Такое решение принято осознанно: для глобальных ачивок, действующих на всём протяжении жизни пользователя, пришлось бы учитывать статистику за прошлые годы и отслеживать её изменения в реальном времени. Для MVP эта логика существенно усложнила бы генерацию итогов, поэтому ачивки заранее подготовлены и хранятся как готовые данные пользователя.

## Безопасность данных

MVP работает с тестовыми данными. В recap используются агрегированные показатели: сервис не выводит личные переписки, данные других пользователей или полный список конкретных покупок. Такой подход позволяет показать характер активности пользователя без раскрытия лишней информации.

## Ограничения MVP

- используются заранее подготовленные тестовые профили;
- правила генерации рассчитаны на демонстрационный сценарий;
- авторизация и работа с реальными аккаунтами не входят в MVP;
- публичная share-card и полноценная продуктовая аналитика не реализованы.
